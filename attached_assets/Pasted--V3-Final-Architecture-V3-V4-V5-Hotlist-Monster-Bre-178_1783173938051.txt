【V3 最终数据层重构（Final Architecture）】

目标：

这是 V3 最后一次数据库重构。

以后禁止再新增 V4 / V5。
以后所有策略（Hotlist、Monster、Breakout、AI...）全部使用这一套数据架构。

========================
一、唯一原则
========================

SQLite 不再保存任何永久交易数据。

SQLite 以后只负责：

1. Binance K线缓存
2. Universe缓存
3. 临时扫描缓存
4. Runner缓存
5. Monster Dataset缓存

任何部署后可以重新生成的数据，都放 SQLite。

========================
二、PostgreSQL 成为唯一永久数据库
========================

所有需要长期保存的数据全部迁移 PostgreSQL。

包括：

v3_candidates

v3_push_queue

v3_paper_orders

v3_order_events

v3_feature_store

v3_strategies

strategy_weekly_reports

strategy_monthly_reports

strategy_versions

future_ai_training

以后所有统计全部来自 PostgreSQL。

========================
三、SQLite 删除职责
========================

禁止再写：

v3_candidates

v3_push_queue

v3_paper_orders

v3_order_events

v3_feature_store

SQLite 中若还有这些表，仅保留兼容读取。

全部改写 PostgreSQL。

========================
四、Repository 重构
========================

建立统一 Repository。

禁止业务代码直接访问 SQLite。

所有模块：

Strategy

Risk

Dedup

Telegram

Paper

Settlement

Performance

统一调用：

StorageRepository

StorageRepository 自动决定：

Cache → SQLite

History → PostgreSQL

以后任何策略不用关心数据库类型。

========================
五、历史数据永久保存
========================

Publish

Redeploy

Reserved VM 重建

全部不能影响：

历史订单

历史信号

历史候选

历史因子

历史绩效

必须永久保留。

========================
六、统一 Signal ID
========================

所有表全部使用：

signal_id

例如：

HOT-20260704-000001

禁止：

symbol+entry

symbol+direction

作为 JOIN。

全部改 signal_id。
